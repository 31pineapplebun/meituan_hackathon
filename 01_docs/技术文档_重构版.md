# 技术文档（React + FastAPI 重构版）

> 外呼指令遵循自动评测系统 —— 前端从 Streamlit 重构为 React + Vite，后端用 FastAPI 把既有评测引擎包成 REST 接口。
>
> 本文档描述**重构后**的系统:整体架构、前端技术栈、后端技术栈、接口契约、数据流、部署运行,以及 Streamlit → React 的取舍。

---

## 1. 项目概述

输入「一条任务指令 + 一个待测模型」,系统用大模型模拟多类用户(8 种 persona)与被测模型做多轮对话,自动判定每条约束是否遵守,产出 **0–100 分 + 五维细分 + 可定位到具体约束的可解释报告**。

把外呼质检从「人工逐条审听」(慢/贵/不一致)升级为「机器自动评测 + 人工监督」。

---

## 2. 重构背景与动机

| | 旧版 | 重构版 |
|---|---|---|
| 前端 | Streamlit(Python 脚本即 UI) | **React 18 + Vite**(多页 SPA) |
| 前后端边界 | 无(UI 直接 import 评测代码) | **REST 接口**(FastAPI),前后端解耦 |
| 评测引擎 | Python | **不动**,原样复用 |

**为什么迁移**(核心叙事):

- **Streamlit 适合快速原型,不适合生产 / 定制 UI**:它每次交互重跑整个脚本、状态靠 `st.session_state` 隐式维护、定制样式要靠注入 CSS hack(`data-testid` 选择器),交互模型和组件复用都受限。
- **React + FastAPI 是标准的前后端分离**:前端是真正的组件化 SPA(可控的渲染、路由、状态),后端是清晰的 REST 接口(可被任意客户端调用、可独立部署 / 扩展)。
- **关注点分离**:UI 逻辑(React)/ 接口编排(FastAPI)/ 评测算法(既有引擎)三层各司其职。

> 原则:评测引擎是经过验证的资产,**只做封装不重写**。重构的边界严格限定在「UI + 接口层」。

## 3. 整体架构

```
┌─────────────────────────────────────────────┐
│ 11_web_frontend  (React 18 + Vite)            │   浏览器 SPA
│  配置 / 运行 / 报告 / 详查 / 单通质检 / 关于    │
└───────────────┬─────────────────────────────┘
                │  REST (原生 fetch, /api/*)
                │  开发期 Vite 代理 → 127.0.0.1:8000
                ▼
┌─────────────────────────────────────────────┐
│ 12_api  (FastAPI + uvicorn)                   │   接口 / 编排层
│  config(配置空间) · engine(引擎桥接)         │
│  jobs(异步任务 + 轮询) · main(路由)          │
└───────────────┬─────────────────────────────┘
                │  Python 函数调用(sys.path 桥接,不改引擎)
                ▼
┌─────────────────────────────────────────────┐
│ 既有评测引擎(07_simulator / 08_parser /      │   评测内核(不动)
│ 09_pipeline)                                  │
│  Parser · 8 Persona 模拟器 · 5 类 Verifier ·   │
│  P3 三层评分 · 模型级聚合                       │
└─────────────────────────────────────────────┘
```

三层职责:
- **前端**:渲染 UI、收集配置、发请求、轮询进度、画图表。无任何评测算法。
- **接口层(FastAPI)**:校验入参、把请求翻译成对引擎函数的调用、用后台线程跑耗时评测、用 job + 轮询暴露进度。**不含评测逻辑,只做桥接和编排**。
- **评测引擎**:原样复用 `model_evaluation.run_fast_demo / run_full_evaluation`、`pipeline.run_pipeline`、`08_parser.parse_instruction` 等既有函数。

## 4. 前端技术栈(`11_web_frontend/`)

| 技术 | 选型 | 用途 / 理由 |
|---|---|---|
| **React 18** | 函数组件 + Hooks | UI 框架;只用函数组件 + Hooks,不用 class |
| **Vite** | `^5.4` | 构建 + dev server;dev 期把 `/api` 代理到 FastAPI(同源、免跨域) |
| **React Router** | `react-router-dom ^6` | 多页路由(`/config /run /report /detail /single /about`)+ 共享布局 `<Outlet/>` |
| **React Context** | 内置 | **跨页共享状态**(评测配置 / 运行状态 / 结果),切页不丢 |
| **react-plotly.js** | `^2.6` + `plotly.js-dist-min ^2` | 图表(雷达 + 甜甜圈),沿用原 Plotly,迁移成本最低 |
| **原生 fetch** | 浏览器内置 | API 封装(`api/evalApi.js`),请求显式可见,不引 axios |
| **CSS Modules** | Vite 内置 | 组件级样式隔离(`*.module.css`) |
| **JavaScript(JSX)** | — | 暂不用 TS(先把 React 吃透) |

> 依赖克制:不引重型 UI 库(Antd/MUI)、不引状态管理库(Redux/Zustand)—— Context 足够。

### 4.1 目录结构

```
11_web_frontend/
├── index.html, vite.config.js, package.json
└── src/
    ├── main.jsx              # 入口:EvalProvider 包在 RouterProvider 外(切页不丢状态)
    ├── App.jsx               # 外层布局(头部 + 步骤导航 + <Outlet/>)
    ├── router.jsx            # 路由表
    ├── api/evalApi.js        # FastAPI 接口封装(原生 fetch)
    ├── context/EvalContext.jsx  # 跨页共享状态(配置/jobId/报告/详查选中)
    ├── constants/labels.js   # 维度/persona/verifier 标签 + 配色(集中一处)
    ├── pages/
    │   ├── ConfigPage.jsx    # 受控表单:指令 / 模型 / persona / 模式
    │   ├── RunPage.jsx       # 异步状态机:轮询任务进度 + useEffect 清理
    │   ├── ReportPage.jsx    # 模型级报告 + Plotly 图表 + 下载
    │   ├── DetailPage.jsx    # 单通详查(从报告下钻)
    │   ├── SinglePage.jsx    # 单通质检(粘贴对话 / 大致描述模拟)
    │   └── AboutPage.jsx     # 方法论 + kappa
    └── components/           # RadarChart / DonutChart / ScoreCard / PersonaBars /
                              # WeakConstraintsTable / VerdictTable / Transcript /
                              # ProgressBar / Loading / SingleReport
```

### 4.2 重点体现的 React 概念

- **React Router 多页路由**:`createBrowserRouter`,`App` 作外层布局,子页渲染到 `<Outlet/>`。
- **Context 跨页状态共享**:`EvalContext` 持有配置表单、`jobId`、报告结果;`EvalProvider` 包在 `RouterProvider` 外,所以路由切换不卸载它、结果不丢。页面内的临时状态(loading / 错误)仍用 `useState`——**该上 Context 的才上,不滥用**。
- **受控表单**:`ConfigPage` 所有输入 `value` + `onChange` 绑到 Context 的 `form`。
- **耗时任务的异步状态机 + 轮询 + `useEffect` 清理**(核心):`RunPage` 是一个状态机 `polling → fetching → report / failed`:`POST /api/evaluate` 拿到 `job_id` 后,用 `setTimeout` 轮询 `GET /api/jobs/{id}`,完成再取报告;`useEffect` 的清理函数用 `cancelled` 标志 + `clearTimeout` 防止卸载后继续 setState / 轮询泄漏。
- **列表 / 表格用稳定 key**:用后端 id(`dialogue_id` / `constraint_id`),不用数组下标。
- **组件拆分 + 图表封装**:图表(雷达 / 甜甜圈)封装成独立组件,数据从 props 进,组件本身无状态。

### 4.3 图表接入

用 `react-plotly.js` 的 **factory + `plotly.js-dist-min`**(而非默认完整 `plotly.js`)接入,打包更友好:

```js
import createPlotlyComponent from 'react-plotly.js/factory'
import Plotly from 'plotly.js-dist-min'
const Plot = createPlotlyComponent(Plotly)
```

沿用原 Streamlit 的两张图:五维能力雷达(`scatterpolar`,闭合多边形)+ 约束校验方式分布甜甜圈(`pie` + `hole`,ColorBrewer Set2 配色)。

## 5. 后端技术栈(`12_api/`)

| 技术 | 用途 |
|---|---|
| **FastAPI** | REST 路由 + 入参校验(Pydantic 模型) |
| **uvicorn** | ASGI server |
| **pydantic** | 请求体校验 |
| 标准库 `threading` | 后台线程跑耗时评测 + 内存任务存储 |

四个模块,职责单一:

- **`config.py`** — 配置空间(单一事实来源):内置指令路径 / 待测模型 / 8 persona / 5 评分维度。前端 `GET /api/config` 拉它来动态渲染表单。
- **`engine.py`** — **引擎桥接层**(重构的关键):复刻 `sys.path` 设置后,直接调用既有引擎函数(`run_fast_demo` / `aggregate_model_report` / `run_full_evaluation` / `run_pipeline` / `parse_instruction`)。**不复制任何评测逻辑**。
- **`jobs.py`** — 轻量级内存任务存储 + 后台线程执行器:支撑「提交即返回 `job_id`、后台跑、前端轮询」。带任务数上限(淘汰最老的已结束任务)。
- **`main.py`** — FastAPI 路由 + CORS + 启动清理(lifespan)。

### 5.1 接口契约

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/config` | 配置空间(指令 / 模型 / persona / 维度) |
| POST | `/api/evaluate` | 提交配置(内置指令 fast/full 或自定义指令)→ 启动后台评测 → `{job_id}` |
| GET | `/api/jobs/{id}` | 轮询任务状态 / 进度(`running / done / failed` + `progress`) |
| GET | `/api/report/{id}` | 取模型级评测报告 |
| GET | `/api/instruction/{id}/md` | 取内置指令原文(供自定义指令做模板) |
| POST | `/api/eval-dialogue` | 单通质检:用户给一通对话 → 单通报告 |
| POST | `/api/simulate-eval` | 据描述模拟一通对话再质检(需 key) |

### 5.2 为什么用「job + 轮询」而不是同步返回

完整评测要几分钟(逐 persona 模拟对话 + 评测)。`POST /api/evaluate` 立刻返回 `job_id`,真正的评测在**后台守护线程**里跑,引擎的 `progress_callback` 把进度写进任务;前端轮询 `GET /api/jobs/{id}` 拿进度,完成后再取报告。这样请求不会超时,前端能显示实时进度。

## 6. 评测引擎(不动,概览)

重构未改动这一层,简述其能力以便理解全貌:

- **Parser**(`08_parser`):任务指令 Markdown → 原子约束清单 JSON(每条标注 verifier 类型 + 评分维度 + 是否 critical / 红线)。
- **8 Persona 用户模拟器**(`07_simulator`):合作 / 坚持拒绝 / 越界 / 打断 / 状态 / 模糊 / 对抗 / 提问。
- **5 类 Verifier 分层判定**(`09_pipeline`,按成本分层):`rule` / `rule_pattern`(0 次 LLM)→ `state_tracker`(关键词优先 + LLM 兜底)→ `llm_extract_then_rule`(1 次)→ `llm_judge`(1 次)。客观约束零成本判定,LLM 预算集中在主观约束。
- **P3 三层评分**:L1 加权(D1 25% + D2 25% + D3 20% + D4 15% + D5 15%)→ L2 Critical 钳制 → L3 红线钳制。
- **模型级聚合**:多通对话 → 模型能力画像(综合分 + 各 persona 分解 + 最弱约束 + 自动诊断)。
- **工程可靠性**:统一 LLM 客户端(重试 / 固定 seed 可复现 / 缓存 / 并发 / 自一致性投票 / 鲁棒 JSON 解析)。

两种评测模式:**快速演示**(读 `09_pipeline/model_demo/` 预置的真实结果,秒出、无需 key)、**完整运行**(实时真跑,需对应模型 API key)。

## 7. 核心数据流(一次评测)

```
ConfigPage(受控表单)
  → POST /api/evaluate  ──→ jobs.create_job() + 后台线程跑 engine.run_fast/run_full
  ← { job_id }
RunPage(状态机)
  → 轮询 GET /api/jobs/{job_id}  ←  progress { current, total, msg }
  → status=done → GET /api/report/{job_id}  ←  模型级报告 dict
  → 存入 EvalContext → 跳转 ReportPage
ReportPage
  → ScoreCard + RadarChart(dim_avg) + PersonaBars + WeakConstraintsTable + DonutChart
  → 点 persona 行 → DetailPage 下钻(对话回放 + 逐约束判定 + 五维雷达)
```

## 8. 部署与运行

### 后端
```bash
cd 12_api
python -m pip install -r requirements.txt        # fastapi + uvicorn
python -m uvicorn main:app --app-dir . --port 8000
# 完整运行 / 自定义指令真跑需对应 key: export DEEPSEEK_API_KEY=... / OPENAI_API_KEY=...
```

### 前端
```bash
cd 11_web_frontend
npm install
npm run dev        # http://localhost:5173 (dev 期 /api 代理到 127.0.0.1:8000)
npm run build      # 产出 dist/(生产可由任意静态服务器托管)
```

> dev 期 Vite 代理目标用 `127.0.0.1`(非 `localhost`):Windows 上 `localhost` 可能解析到 IPv6 `::1`,而后端默认绑 IPv4,会导致代理连不上。

## 9. 工程细节(重构期处理的几个点)

- **引擎导入的环境耦合**:verifier 在首次 import 时读 `VERIFIER_LLM_MODEL`(import 时常量)。桥接层在调用前设好环境变量;`run_fast_demo`/`aggregate_model_report` 是纯 dict 处理、不触发重导入,所以快速演示路径无此约束。完整运行在长驻进程内连续切换不同被测模型有此限制(已注释,生产可用子进程隔离)。
- **任务存储有界**:`jobs._jobs` 设 `MAX_JOBS` 上限,淘汰最老的已结束任务,避免长跑进程内存只增不减。
- **临时文件清理**:自定义指令评测落临时 parsed.json 到专用目录,FastAPI 启动时 sweep,避免 daemon 线程被强杀时残留。
- **可访问性**:报告页可点击的 persona 行做成键盘可达(`role="button"` + `tabIndex` + `onKeyDown`)。
- **取消**:运行页提供「取消并返回」(前端停止轮询;后端线程为简单起见仍跑完,生产可加协作式取消)。

## 10. Streamlit → React 的取舍(一句话能讲清)

- **Streamlit 的好**:Python 一把梭、几十行就有能跑的 UI,**适合快速验证想法 / 内部小工具 / 数据脚本可视化**。
- **Streamlit 的限制**:重运行模型(每次交互重跑脚本)、状态隐式、组件 / 样式 / 路由定制能力弱、前后端不分离 —— **不适合需要精细交互、可维护、可独立部署的生产前端**。
- **迁到 React + FastAPI 换来**:真正的组件化与状态控制、清晰的多页路由、可被任意客户端复用的 REST 后端、前后端可独立部署与扩展。代价是要写更多「胶水」(接口、状态、轮询),但换来可维护性与产品化能力。

> 结论:用 Streamlit 把评测引擎快速跑通验证,再用 React + FastAPI 做成可维护、可部署的产品形态 —— 这正是这次重构的价值。

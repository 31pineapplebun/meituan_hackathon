## 1. 问题定义

### 1.1 业务背景：履约数字人外呼

在美团的履约数字人外呼场景中，系统自动发起与用户（骑手 / 商家 / 求职者）的通话，由对话模型按预设的**任务指令**完成具体任务。赛题方（一招老师）在直播中点名了三类典型场景：

- **AI 站长**：定时给骑手打电话——提醒出勤、提醒注意安全、通知线下培训等；
- **自动化招聘**：定期招聘骑手，走自动化招聘流程；
- **骑手助手**：定期帮骑手解决问题——商家出餐慢、用户反馈送餐晚、地图定位不准等。

数据形态上，用户语音已通过 ASR 转为文本，因此本题只需处理**文本对话**。组委会提供的脱敏数据仅有 **2 条**指令样本（外卖飞毛腿骑手通知、直播课程升级告知），无真实对话数据，要求参赛方"根据场景自行模拟"。

### 1.2 待评估的能力：指令遵循

一条外呼**任务指令**本质上是给对话模型的一段 prompt，但它远不止"说句话"那么简单——它同时编码了：

- **多步任务流程**：如「确认身份 → 告知事项 → 解答疑问 → 确认意愿 → 礼貌结束」，且常含**条件分支**（若对方不是负责人则请其转达；若用户表示开车则礼貌挂断）；
- **多类原子约束**：字数上限、禁用词、固定话术、禁止承诺（折扣/补贴）、FAQ 知识正确性、流程顺序、口语化语气、适时终结等。

两个官方样本的复杂度即可见一斑（实测，解析器自动拆解）：

| 官方样本 | 流程 Step | FAQ | 原子约束数 |
|---|---|---|---|
| 样本 1 · 飞毛腿合同通知 | 4 | 5 | 6（解析后细化为 15 条原子约束）|
| 样本 2 · 课程升级告知 | 7（含嵌套子步骤 + 多分支）| 4† | 11（解析后细化为 21 条原子约束）|

> † 样本 2 原文无独立 `# Knowledge Points (FAQ)` 段，知识点隐含在「按知识库作答」等流程节点中，解析器将其归并为 **4 条**知识点（与 `parsed_examples/official_2_kecheng_parsed.json` 一致）。

"指令遵循能力评估"要回答的核心问题是：**待测模型在真实对话压力下，逐条约束、逐个流程节点，到底遵循得怎么样？** 这无法用一个 0/1 的"对/错"概括，必须可解释、可量化、可定位短板。

### 1.3 痛点：人工质检 慢、贵、不一致、难量化、难给方向

赛题直播中，命题嘉宾（一招老师）明确点出了痛点——"人工评估……整个评估的耗时会非常长……没办法大批量执行……也很难有一个很统一的指标"（直播讲解原话转述）。综合可拆为五条：

1. **慢**：人工逐通逐约束审，"评估耗时非常长，没办法大批量执行"。单通人工评估约 **10–30 分钟**（估算，外呼/客服质检经验值）。
2. **贵**：人力成本随通话量线性增长；模型每次迭代都要重新全量评估，重复投入。
3. **不一致**：约束判定（尤其口语化、流程是否到位等主观项）人与人之间分歧大，缺乏统一裁判标准。
4. **难量化**：赛题明确要求 **0–100 分**而非 0/1，人工往往只能给"还行/不太行"的模糊印象，难以横向比较模型。
5. **难给优化方向**：赛题与直播都强调要输出"优化方向"，但人工抽检难以系统化地汇总"模型到底弱在哪类约束、哪个流程节点"。

### 1.4 赛题对评测系统的硬性要求

赛题与直播明确了**五条**硬性要求（下表前五行）；我们在此之上主动补强了"可靠性"作为第六条——它不是赛题原文要求，而是我们为让评测结果可信而自加的保障。它们既是交付门槛，也是本系统的设计目标：

| 要求 | 含义 | 本系统的对应设计（详见后续章节）|
|---|---|---|
| **可解释** | 每个判定都能追溯到对话中的具体证据 | 每条约束输出 verdict + evidence（引用 turn 原文）+ reason |
| **可量化** | 0–100 分，而非 0/1 | P3 三层评分算法（第 3 章）|
| **可靠**（团队补强，非赛题原文要求）| 判得准不准要有数据证明 | Kappa 实证 + 三路 LLM 对照（第 5 章）|
| **充分有效** | 用户模拟器覆盖各类约束与用户行为 | 8 Persona 用户模拟器（第 3 章）|
| **优化方向** | 必须告诉用户怎么改进 | 自动优化建议 + 最弱约束/persona 定位（第 3、7 章）|
| **一站式** | 完整端到端流程，非脚本拼凑 | Streamlit 一站式平台：选指令 → 选模型 → 评测 → 画像 |

### 1.5 人工评测 vs 自动评测：量化对比

| 维度 | 人工评测 | 本系统 |
|---|---|---|
| 单通评测耗时 | 约 10–30 分钟（估算）| **数十秒级**（实测，含多约束 8 路并发判定）|
| 单通评测成本 | 按时薪约 ¥10–30（估算）| **约 ¥0.2**（估算，基于 deepseek-flash token 成本）|
| 评测一致性 | 人与人之间约 κ≈0.4（估算，业界主观标注水平）| 与人工 **κ=0.4483**、客观约束 **κ=1.0**、三路 LLM 互查 **κ=0.81**（实测，详见第 5 章）|
| 可规模化 | 受限于人力，难以大批量 | 可固定随机种子复现、结果缓存、并发批量评测 |
| 可复现 | 同一通对话不同人/不同时judge结果会漂移 | 固定对话 + 固定种子 + 缓存 → **逐字节可复现**（实测）|

> 注：表中"人工 κ≈0.4"为**人际**一致性的业界估算，本系统"κ=0.4483"为**机器–人工**一致性，两者口径不同、仅作量级参照（且均受类别不平衡影响）；详见第 5 章「Kappa 悖论」的诚实讨论。

> **小结**：外呼质检的本质矛盾是——业务侧需要**频繁、规模化、可比较**地评估对话模型的指令遵循能力，而人工评测在速度、成本、一致性、可量化、可定位方向五个维度上同时受限。本系统的目标，就是把这件事从"靠人审"升级为"机器审 + 人监督"的工业级可信流程。后续章节依次给出系统架构（第 2 章）、核心技术（第 3 章）、工程与评测可靠性（第 4、5 章）、标注迭代故事（第 6 章）与真实应用效果（第 7 章）。

## 2. 系统架构与数据流

### 2.1 一句话架构

系统是一条**端到端流水线**：一份任务指令 + 一个待测模型进去，一份「0–100 分 + 逐约束证据 + 优化方向」的能力画像出来。中间分四个阶段——**解析 → 模拟 → 判定 → 聚合**——每个阶段都有明确的输入/输出契约；所有 LLM 调用统一收敛到一个客户端层集中治理（重试 / 种子 / 缓存 / 鲁棒解析），而非散落在各模块。

### 2.2 端到端数据流图

```
┌──────────────┐  Role / Task / Constraints / FAQ / Call Flow + 变量(${X})
│ 任务指令 .md  │
└──────┬───────┘
       │ ① 解析器  08_parser/parser.py
       │   规则提取(确定性) + LLM 打标签(5 维) + 自动注入(流程→约束 / META 约束)
       ▼
┌────────────────────────────────────┐   每条原子约束都带:
│ 约束清单 JSON (16–36 条原子约束)     │   verifier 类型 / 评分维度 D1–D5 /
│ atomic_constraints + faq + flow_steps│   是否 critical / 是否红线 / 权重
└──────┬─────────────────────────────┘
       │                                       ┌─ 待测模型 M  → assistant
       │ ② 用户模拟器  07_simulator/simulator_v2 ┤
       │    8 Persona × M  → 多通对话(双 LLM 对打) └─ Persona     → user
       ▼
┌──────────────┐
│ 多通对话 JSONL│  (turn / role / content)
└──────┬───────┘
       │ ③ 评测  09_pipeline/pipeline.py: run_pipeline
       │    逐约束 dispatch → 5 类 Verifier 并发判定(线程池, 默认 8)
       │    → compute_p3_score: L1 加权 · L2 Critical 钳制 · L3 红线钳制
       ▼
┌──────────────────┐
│ 单通评分 + 逐约束 │  verdict(pass/fail/na/not_implemented/error) + evidence + reason
│ 证据 + 优化建议   │
└──────┬───────────┘
       │ ④ 聚合  09_pipeline/model_evaluation.py: aggregate_model_report
       ▼
┌───────────────────────────────────────────────┐
│ 模型能力画像: 综合分(0–100) + 5 维雷达 + 各 Persona │
│ 分解(最弱在前) + 最弱约束 Top10 + 自动诊断 + 优化方向 │
└───────────────────────────────────────────────┘
        ↑ 所有 LLM 调用统一经 09_pipeline/llm_client.py (重试 / seed=42 / 缓存 / 鲁棒 JSON)
```

### 2.3 四个阶段详解

#### 阶段 ① 解析器：任务指令 → 原子约束清单（`parser.py`）

把一段自然语言任务指令拆成**机器可逐条判定**的原子约束，是整条流水线的地基。解析器分三层：

1. **规则提取层（确定性）**：按 Markdown 结构抽取 `# Role / # Task / # Constraints / # Knowledge Points (FAQ) / # Call Flow` 各段，并抓出 `${X}` 类变量、数字编号/短横线列表的约束项、主步骤与子步骤（如 `3.1`）。这一层不调 LLM，稳定可复现。
2. **LLM 打标签层**：对每条约束调用 LLM，打 5 个结构化标签——`name`（规范化约束名）/ `scoring_dimension`（D1–D5 五维之一）/ `verifier`（5 类判定器选一）/ `is_critical`（是否关键约束）/ `weight`（1–5 权重）。这一步把"人话约束"翻译成"评分引擎能消费的结构"。
3. **自动注入层**：① 每个流程 Step 自动转成一条 `state_tracker` 约束（维度 D1、critical、权重 3）；② 注入最多 5 条 `[META]` 标准约束（开场白须含变量、变量无残留、任务核心意图达成、适时终结、FAQ 知识正确）——没有变量或 FAQ 时自动跳过对应项。

> **约束清单的三个来源**：最终的"原子约束总数"由「指令显式约束 + 流程步骤转换 + META 注入」三部分构成。这解释了为何样本 1 的 6 条显式约束会细化为 **15 条**、样本 2 的 11 条细化为 **21 条**——多出来的是流程节点与标准元约束。

#### 阶段 ② 用户模拟器：8 Persona × 待测模型 → 多通对话（`simulator_v2.py`）

赛题明确要求"用户模拟器需自行构建，且要尽量覆盖任务指令里的所有情况"。我们用 **8 种 Persona**（4 核心 + 4 扩展）做"双 LLM 对打"——待测模型扮演 assistant（系统提示=任务指令），Persona 扮演 user（系统提示=该 Persona 的行为剧本）：

| | Persona | 探测的能力 |
|---|---|---|
| 核心 | 🤝 配合型 / 😤 坚持拒绝型 / 🌀 越界提问型 / ✋ 打断型 | 主流程 / 礼貌挂断 / 守边界 / 过渡语恢复 |
| 扩展 | 🚗 状态型(忙·开车) / 🤔 模糊型 / ⚔️ 对抗型 / ❓ 提问型 | 状态话术 / 推进含糊对话 / 守红线(禁承诺) / FAQ 覆盖 |

对话在命中结束关键词（assistant 端"再见/挂断/稍后再打/祝您…"，或 user 端"挂了/再见"）或到该 Persona 的 `max_turns` 时停止，并记录结束原因（assistant 主动 / user 主动 / 到达上限）。**关键工程细节**：喂给被测模型的指令文本会先做变量替换（`${Y}`→具体值），避免模型复读或瞎编占位符污染对话；而用于评测的约束仍保留 `${Y}` 规范形式。

#### 阶段 ③ 分层 Verifier：逐约束并发判定（`pipeline.py` + `verifier_*.py`）

`run_pipeline` 对约束清单逐条 `dispatch`：按约束的 `verifier` 字段在注册表中查到对应判定器，用线程池**并发**执行（默认 8 路；LLM 调用是 IO 密集型，并发显著提速）。每条判定包一层 `_safe_dispatch`——单条约束抛异常只记为该条 `error`，**不拖垮整通评测**。

5 类判定器按"成本从低到高"分层（详细判定逻辑见第 3 章）：`rule` / `rule_pattern`（纯规则，0 次 LLM）→ `state_tracker`（关键词+同义词优先，命中即过、0 次 LLM，不可靠时才调 LLM 兜底）→ `llm_extract_then_rule`（1 次 LLM 抽事实 + 规则判定）→ `llm_judge`（LLM 直接判，关键约束走 3 次自一致性投票）。每条判定统一产出 5 种 verdict 之一：`pass / fail / na / not_implemented / error`。

#### 阶段 ④ P3 评分 + 模型级聚合 → 能力画像（`model_evaluation.py`）

单通评分由 `compute_p3_score` 三层产出（L1 五维加权 / L2 Critical 钳制 / L3 红线钳制，数字与算法见第 3 章）；**只有 `pass`/`fail` 计入分母**，`na`/`not_implemented`/`error` 跳过，全部不可计分时返回 `final_score=None`（标记"不可评测"，**不是 0 分**）。多通对话再由 `aggregate_model_report` 聚合成画像：

- **综合分** = 各可评测场景的均分（不可评测场景单独剔除并提示，避免被误读为"模型很差"）；
- **Persona 分解**（最弱在前，便于定位短板）、**5 维平均**、**最弱约束 Top10**（跨场景失败率）；
- **自动诊断**：按综合分给等级（≥85 优秀 / ≥70 良好 / ≥50 需改进 / <50 不合格）+ 一句话评语 + 优化方向。

### 2.4 三个关键架构决策

1. **统一 LLM 客户端（`llm_client.py`）**：所有判定/抽取的 LLM 调用都走它——重试（默认 3 次）、固定种子（seed=42）、结果缓存、鲁棒 JSON 解析集中治理。Verifier 不直接碰 SDK，因此"可复现/省额度/抗抖动"是全局属性而非各处重复造轮子。
2. **双运行模式**：**完整运行**（真调模型生成对话 + 真判定，需 API key）用于真实评测；**快速演示**（直接读预生成的真实评测结果 `model_demo/*.json`，秒出）用于现场演示——演示数据是真跑产物而非 mock 编造。
3. **指令无关的流水线**：阶段 ①→④ 不绑定任何具体任务——`run_full_evaluation` 接受任意"已解析约束清单 + 指令原文"，因此换一份新指令即可复用整条链路。这是"一站式、可泛化"的结构基础。

## 3. 核心技术点

本章深挖四个核心设计：分层 Verifier（为何又准又省）、P3 三层评分（为何防得住虚高分）、8 Persona 模拟器（为何覆盖得全）、模型级聚合（为何能定位短板）。

### 3.1 五类分层 Verifier：按"成本最低能判则不升级"分层

把不同类型的约束交给不同"判定器"，是本系统准确性与成本控制的核心。五类判定器按 LLM 成本从低到高排列，每条约束只用"能判得准的最低成本手段"：

| Verifier | 判定方式 | LLM 调用 | 典型约束 |
|---|---|---|---|
| `rule` | 确定性规则（正则） | **0 次** | 字数上限（"30 字以内"）、变量残留（`${X}` 未替换）|
| `rule_pattern` | 关键词 / 正则匹配 | **0 次** | 禁用词（"好的/哈哈"）、开场白合规 |
| `state_tracker` | 关键词+同义词优先，**命中即过**；不可靠才调 LLM | **0 次**（命中）/ 1 次（兜底）| 流程 Step 是否覆盖（"告知培训时间地点"）|
| `llm_extract_then_rule` | LLM 抽事实 + Python 规则判 | 1 次 | 禁止承诺、越界提问应答、FAQ 知识、条件响应 |
| `llm_judge` | LLM 直接判 pass/fail | 1 次（关键约束 3 次投票）| 口语化、避免重复、适时结束、给发言机会 |

**这套分层的真实价值（实测，基于两个官方样本的 verifier 分布）：**

| 样本 | 纯规则(0 LLM) | state_tracker | 必走 LLM(extract+judge) |
|---|---|---|---|
| 样本 1（15 约束）| 2（13%）| 4 | 9（60%，其中 llm_judge 7）|
| 样本 2（21 约束）| 1（5%）| 7 | 13（62%，其中 llm_judge 11）|

诚实地说：这两个样本的约束**以主观判断为主**（口语化、收尾、知识准确等），这类约束天然必须用 LLM。因此分层带来的 LLM 调用节省，**乐观上界约为 38–40%**（估算：纯规则 + 假设全部 state_tracker 关键词命中而不调 LLM），而非更高。分层的核心价值不在于"省下一个固定百分比"，而在于：

1. **客观约束零成本且更准**：字数、禁用词、变量残留这类有确定答案的约束，用规则判比用 LLM 判**又快又稳又省**——把 LLM 判这些反而会引入抖动；
2. **把 LLM 预算集中在真正需要语义理解的地方**：只有"模型说得是否口语化、是否答到点上"这类主观约束才花 LLM；
3. **关键约束用自一致性换可靠**：`is_critical` 约束走 3 次投票取多数，用"多花 2 次调用"换取关键判定不被单次抖动带偏。

> **工程纪律**：`llm_extract_then_rule` 的 prompt **只让 LLM 抽取事实（输出 JSON），判定交给 Python 规则**——避免"让 LLM 既当运动员又当裁判"。这是降低主观性、提升可复现的关键设计。

### 3.2 P3 三层评分：防止"D3 满分但流程全崩"的虚高分

一个对话模型可能"该说的约束都说了，但流程乱套"或"踩了安全红线"。如果只做加权平均，会给出误导性的高分。P3（Protect-Penalize-Pinpoint）用三层把这种虚高分钳住（数字与算法实测，见 `04_scoring/scoring_validation.py`，4/4 场景测试通过）：

**L1 · 五维加权**（满数据下的标称权重，和为 1.0）：

| 维度 | 权重 | | 维度 | 权重 |
|---|---|---|---|---|
| D1 流程遵循 | 0.25 | | D4 知识准确 | 0.15 |
| D2 任务完成 | 0.25 | | D5 对话质量 | 0.15 |
| D3 约束遵循 | 0.20 | | | |

每个维度分 = 该维度内**通过约束的权重和 / 该维度总权重 × 100**；`raw_score = Σ(维度分 × 维度权重)`。若某维度无数据，按"已用权重之和"重新归一化，避免分数被无关维度拉低。

**L2 · Critical 钳制**——关键约束通过率直接决定分数上限：

| 关键约束通过率 | 分数上限 |
|---|---|
| = 100% | 100 |
| ≥ 90% | 85 |
| ≥ 70% | 65 |
| ≥ 50% | 45 |
| < 50% | 30 |

**L3 · 红线钳制**——任一红线约束（`is_red_line`，如"禁止承诺折扣""用户开车须礼貌挂断"）被违反，**分数上限直接压到 40**。生产路径（`pipeline.py`）的红线是**数据驱动**的：读每条约束的 `is_red_line` 字段，由指令侧标记。

最终：`final_score = min(raw_score, min(critical_ceiling, red_line_ceiling))`。四个回归场景验证了三层协同生效（实测）：理想对话 ≥90、中规中矩 75–87、流程缺失 55–70、红线翻车 **≤40**。

> **口径说明**：只有 `pass`/`fail` 计入分母，`na`（条件未触发）/`not_implemented`（mock 未覆盖）/`error` 都跳过，不稀释也不拉低分数；全部不可计分时返回 `final_score=None`（标记"不可评测"，**不是 0 分**——见第 4 章空对话保护）。

### 3.3 八 Persona 用户模拟器：覆盖"任务指令里的所有情况"

赛题明确要求"用户模拟器需自行构建，且要尽量激发、覆盖任务指令里的所有情况"。单一"配合型"用户只能测出 happy path，测不出模型在压力下的边界行为。我们设计 8 种 Persona，每种对应一类必须被覆盖的约束 / 流程分支（详见第 2 章 §2.3 表）：配合型测主流程，拒绝型测"安慰后挂断"，越界型测"指定话术守边界"，打断型测"过渡语恢复"，状态型测"开车/忙的规定话术"，模糊型测推进能力，对抗型测"诱导承诺时守红线"，提问型测 FAQ 知识覆盖。

实现上是**双 LLM 对打**：待测模型扮 assistant（系统提示=任务指令），Persona 扮 user（系统提示=行为剧本），各带重试与空回复保护；命中结束语或到该 Persona 的 `max_turns`（8–16 不等）即停，并记录结束原因。**关键修复**：喂给被测模型的指令文本会先把 `${Y}` 等变量替换成具体值，避免模型复读/瞎编占位符污染对话（而评测用的约束仍保留 `${Y}` 规范形式）——这是分数可复现的前提之一。

### 3.4 模型级评测聚合：从"单通分"到"可定位短板的能力画像"

`aggregate_model_report` 把多通对话的单通结果聚成模型画像，指标口径如下（实测，`model_evaluation.py`）：

- **综合分** = 各**可评测**场景 `final_score` 的均分（另给 min/max 范围）；不可评测场景（空对话/API 失败，`final_score=None`）单独计数并在诊断里提示，**不计 0 分**——避免把"没测成"误读为"模型很差"；
- **Persona 分解**：每通记综合分 / 关键通过率 / 钳制上限 / 轮数，**按分数升序（最弱在前）**，一眼定位模型在哪类用户下最弱；
- **5 维雷达** + **最弱约束 Top10**（跨场景失败率降序，分母只算 pass+fail），定位"弱在哪个维度、哪条约束"；
- **自动诊断**：按综合分给等级（≥85 优秀 / ≥70 良好并点名最弱 persona / ≥50 需改进 / <50 不合格）+ 一句话评语 + 优化方向。

这一层正是赛题要的"**可量化 + 可解释 + 给优化方向**"的落点：不是一个孤立的 0–100 分，而是"综合分 + 各场景表现 + 最弱约束 + 该往哪改"的完整画像。

## 4. 工程可靠性保障

一个评测系统要真正能用，不能只在理想情况下跑通——外部 API 会抖动、LLM 会偶尔吐出坏 JSON、并发评测会有数据竞争、对话生成可能失败。**评测器本身如果不可靠，它给出的分数就不可信。** 本章是把这套系统从"demo 能跑"做到"工业级可信"的工程内核。

### 4.1 设计内核：把所有外部不确定性收敛到一个治理点

最关键的一条架构决策：**所有 LLM 调用统一走 `09_pipeline/llm_client.py`**，重试、种子、缓存、限流、鲁棒解析在这一层集中治理；各 Verifier 只管"判什么"，不直接碰 SDK。这带来一个重要性质——**可靠性是全局属性，而非每个模块各自重复实现**：改一处重试策略，全系统受益；做一次缓存，所有判定都省。

### 4.2 八项生产级保障

下表每一项都对应一个真实会发生的故障模式（实现见 `llm_client.py` / `verifier_*.py` / `pipeline.py`）：

| 能力 | 实现 | 解决什么故障 |
|---|---|---|
| **智能重试** | 错误分类（429 / 4xx / 5xx / timeout / network / 坏 JSON）+ 仅对可重试错误退避重试（默认 3 次），尊重 `Retry-After` + 随机 jitter、退避封顶 30s | API 限流/抖动/偶发坏 JSON 不再让单条约束变 `error` 污染评分；坏 JSON 自动 re-roll 救回 |
| **可复现（seed）** | 固定 `seed=42` + temperature=0 + 记录模型版本 | 同一通对话今天评与明天评结果一致，经得起复现验证 |
| **结果缓存** | (对话+约束+模型+seed) 哈希缓存；**原子写**（写 `.tmp` 再 rename）+ 写锁 | 重复评测秒出、省 API 费用；并发下不产生半截/损坏的缓存文件 |
| **并发 + 限流** | 多约束并发判定（线程池，默认 8 路）+ 全局在途信号量（`LLM_MAX_INFLIGHT=6`）封顶并发 | 单通评测从数十秒降到数秒，同时避免一拥而上触发供应商限流 |
| **自一致性投票** | 关键约束（`is_critical`）判 3 次、不同 seed、取多数票 | 抹平单次 LLM 判定的偶发抖动，让"红线/关键"判定更稳 |
| **鲁棒 JSON 解析** | `parse_json_robust`：容错 markdown 围栏 / 转义 / 截断 / 缺尾括号 | LLM 输出格式不规整时不再整条评测失败 |
| **同义词容错** | 流程识别内置同义词组（告知≈通知≈跟您说） | 减少"模型说了、但用词不同"的字面假阴性 |
| **空对话保护** | 对话为空/全部约束不可计分时 `final_score=None`（标记不可评测），聚合层剔除而非记 0 分 | 区分"没测成"与"模型真的差"，不给误导性 0 分 |
| **单条隔离** | `_safe_dispatch` 包裹每条约束判定，单条异常只记为该条 `error` | 一条约束抛异常不拖垮整通评测 |
| **可观测统计** | 线程安全的调用统计：calls / cache 命中率 / 重试 / 失败 / p95·p99 延迟 / 错误分类 | 跑批量评测时能看清成本与稳定性，便于诊断 |

> 这套保障不是"锦上添花"——它直接决定评测结论可不可信。例如若没有"空对话保护"，一次 API 失败会被记成 0 分，从而把一个好模型误判为"很差"；若没有"自一致性投票"，一条关键红线约束可能因单次 LLM 抖动而误判。

### 4.3 可复现性实证：从"分数乱跳"到"逐字节一致"

可复现是评测可信的底线，也是本系统踩过坑后专门加固的点。早期完整模式下，由于对话每次重新生成（模拟器走自己的调用、不经统一客户端的缓存/seed），同一配置多次跑分会在 55→90→83 之间乱跳，根本没法写进报告。

解决办法是把"对话生成"与"对话评测"解耦：对话只 live 生成一次并落盘固定，之后评测固定对话——而评测侧（state_tracker 的 LLM 兜底 / llm_extract / llm_judge）全部走统一客户端的 `seed=42` + 缓存，对固定对话就是确定性的。

**实测结果**：两个官方样本用此机制连续两次评测**逐字节一致**——飞毛腿 **63.6**、课程发布 **44.2**（`error=0`，4 个核心 Persona）。这组可复现数字正是第 7 章模型能力画像的数据来源。

> 说明：完整模式下若对话生成异常（如 API key 失效），兜底分支会记 `final_score=0`，这与"空对话不可评测（`None`）"是两种不同语义——前者是真实异常 case，引用时需区分（见第 7 章）。

## 5. 评测可靠性：Kappa 实证与「Kappa 悖论」的诚实讨论

"评测器自己准不准"必须有数据证明，否则它给的分数无人敢信。本章给出本系统与人工标注的一致性实证，并**诚实**讨论一个容易被误读的现象——整体 Kappa 看起来不高（0.45），但这恰恰是 LLM-as-judge 的健康区间，且被"Kappa 悖论"系统性低估了。

> **本章数字均可复现**：整体 Kappa / 一致率为本次用 `06_gold_annotation/kappa_calc.py` 在 1055 条 v6 人工标注 vs deepseek-flash 自动判定上**实跑复现**；维度/verifier 拆解见 `RELIABILITY_REPORT_v2.md`；三路对照见 `batch_results/three_way_summary.json`。

### 5.1 头号数字（实测复现）

在 703 条有效配对（排除 na）上，v6 人工标注 vs 自动评测：

| 指标 | 数值 |
|---|---|
| Cohen's Kappa（整体）| **0.4483** |
| 实际一致率 po | **81.79%**（575 / 703 一致）|
| 随机一致率 pe | 67.00% |

### 5.2 「Kappa 悖论」：为何 po 高达 81.8%，κ 却只有 0.45？

这不是矛盾，而是 Cohen's Kappa 的已知特性。其定义为：

```
κ = (po − pe) / (1 − pe)
```

外呼约束的判定结果**高度不平衡**——绝大多数约束模型都遵守了（pass 占压倒多数）。类别越不平衡，"随机也能蒙对"的概率 pe 就越高（这里 pe=67%）。于是即便实际一致率 po 高达 81.8%，分子 `po−pe` 被压缩，κ 被**系统性低估**——这就是统计学中著名的 **"Kappa 悖论"（high agreement, low kappa）**。

**我们的应对是诚实而非粉饰**：①**同时报告 κ 和 po**，不只报对自己有利的那个；②按维度/类型拆解，让"到底哪类判得准、哪类有分歧"一目了然（见 §5.3），而不是把一个被悖论压低的整体数字当结论。

### 5.3 拆开看：客观类完美，主观类有合理分歧

整体 0.45 一旦拆开，结论非常清晰——**可量化的客观约束接近完美，主观约束才有分歧**：

**按 Verifier 类型**（实测，`RELIABILITY_REPORT_v2.md`）：

| Verifier 类型 | N | po | Kappa |
|---|---|---|---|
| `rule`（字数 / 占位符）| 100 | 100% | **1.0000** |
| `rule_pattern`（禁用词 / 开场白）| 50 | 100% | **1.0000** |
| `state_tracker`（流程）| 218 | 80.3% | 0.003 |
| `llm_extract_then_rule` | 99 | 85.9% | 0.049 |
| `llm_judge`（主观）| 236 | 69.9% | 0.278 |

**按评分维度**：D3 约束遵循度 κ=**0.842**（po 94.3%，顶级一致）；而 D1 流程（κ=0.003）、D5 对话质量（κ=0.265）是主观分歧区。

**这分布完全符合 LLM-as-judge 领域的普遍观察**：客观、有确定答案的约束（字数、禁用词）机器与人 100% 对齐；越主观（口语化、流程是否到位）分歧越大——这反映的是"人类凭整体印象宽容判定 vs 机器按规则严格判定"的本质差异，是**所有** LLM 评测系统的共同课题，而非本系统的特有缺陷。事实上我们抽样独立复核了分歧 case，多数是"机器判得对、人工误标"（详见第 6 章的标注迭代故事）。

### 5.4 三路 LLM 互查：排除"自己跟自己玩"的质疑（实测）

一个自然的质疑是："会不会只是 LLM 自洽、并不可靠？"我们用**三路跨模型族对照**回应——在 10 通均衡样本（每模型 180 条判定）上，让三个独立模型分别判定再两两比对（`three_way_summary.json`）：

| 对照 | 有效 N | po | Kappa |
|---|---|---|---|
| DeepSeek-Flash vs DeepSeek-Pro（同族）| 164 | 92.1% | **0.835** |
| DeepSeek-Flash vs GPT-5-mini（跨族）| 160 | 89.4% | **0.776** |
| DeepSeek-Pro vs GPT-5-mini（跨族）| 160 | 91.9% | **0.833** |
| **三路平均** | — | — | **≈0.81** |

跨 DeepSeek 与 OpenAI 两个**不同模型族**仍达 κ≈0.81，说明评测结论**不依赖单一模型偏差**；且同族 Flash vs Pro 高达 0.835，证明选用更便宜的 flash 不牺牲质量。

### 5.5 诚实的可靠性姿态

学术与业界对 LLM-as-judge 的普遍经验是：**与人工的 κ 落在 0.3–0.6 属健康区间，过高（>0.7）反而要警惕数据泄露或两边犯同样的系统性错误**。我们没有去"刷高"这个数字——相反，第 6 章会讲到：我们早期 v3 标注曾出现 κ=0.72 的"虚高"，后来正是评测系统**自己**发现了那是"人机犯同样错误"导致的假高，并触发了修订。

> **小结**：本系统的可靠性结论是——**客观约束 κ=1.0（完美）、约束遵循维度 κ=0.84（顶级）、整体 κ=0.45（受 Kappa 悖论低估、但同时有 81.8% 实际一致率支撑）、三路跨族互查 κ=0.81（排除单一模型偏差）**。我们选择把这些数字连同它们的局限**一起诚实摆出**——这本身就是一个可信评测系统该有的态度。

## 6. 四轮标注迭代：评测系统反过来发现人类标注的盲区

第 5 章的所有可靠性数字，都是"评测系统 vs 人工 Gold Set"比出来的——**那这把"人工标尺"本身可信吗？** 本章讲一个反直觉但真实的故事：在 4 轮标注迭代中，**评测系统自己发现并修正了人类标注的系统性错误**。这正是工业级评测系统的独立价值——它不只是模仿人，还能纠正人。

> 本章引用的修订日志均在仓库可查：`batch_results/v4_modifications.json`（73 处）、`v5_modifications.json`（50 条）、`audit_findings.json`（11 条标记）。

### 6.1 v3 的"虚高陷阱"（Day 5）

第一轮标注（v3，989 条）与 Claude 副标注员的 Cohen's Kappa 高达 **0.72**，看起来很可信。但这是个**虚高**——人工标注员和 Claude 副标注员**犯了同一个系统性错误**：把"字数超标"的违规错误地归到了"流程结构"约束上。两个标注方向一致地错，一致性自然虚高。这印证了第 5 章的观点：**κ 过高（>0.7）反而要警惕"两边一起错"**。

### 6.2 评测系统独立发现盲区（Day 9）

Day 9 我们用 mock 评测跑了一遍，`audit_findings.json` 自动标记了 **11 条**存在人机分歧的约束，其中有约 **5 条出现"系统性反转"**——机器判定与人工标注方向相反。按"先验证再说话"，我们对这些分歧 case 做了独立抽样复核，结论是**多数为"机器判得对、人工标错"**（典型如：人工因"某轮 45 字超长"把 S1 流程约束标 fail，但字数超标 ≠ 流程没走到，机器正确地把流程判 pass）。

**这一步是关键**：发现盲区的不是又一个人，而是**评测系统本身**——它按规则严格判定，反而照出了人类"凭印象"标注的系统性偏差。

### 6.3 修订闭环（v4 → v5 → v6）

| 版本 | 时间 | 操作 | 标注量 |
|---|---|---|---|
| v3 | Day 5 | 初次标注（虚高）| 989 |
| v4 | Day 9 | 依据审计**自动修订 73 处**（`v4_modifications.json`）| 989 |
| v5 | Day 9 末 | **手工复核 50 条**高风险 case（`v5_modifications.json`）| 989 |
| **v6** | **Day 10** | **全量重标 1055 条**（最终版）| **1055** |

到 v6，不仅重标了全量，标注质量本身也可见地提升：confidence 分布从"全部 high（其实不可信）"变成 **54% high + 41% medium + 5% low**（敢于标注不确定），evidence 也从模糊变为平均约 20 字的精准引用。

### 6.4 诚实说明：两套基线不能混比

迭代过程中出现过两个不同的 Kappa 基线，**必须讲清口径、不能简单说"kappa 降了"**：

- **v3 = 0.72**：是与**同期** Claude 副标注员比、用的是**当时（含瑕疵）的规则**——这个高分恰恰是"人机同错"的虚高；
- **v6 = 0.4483**：是与**自动评测**比、用的是 **Day 10 修订后的新规则**。

两者口径不同，不可直接相减。真实的结论是：**0.72 是被系统性同错抬高的假象，0.4483 才是用修订后规则得到的、经得起复核的可信值**。承认并修正 v3 的瑕疵，是诚实的科研态度，也是评测系统价值的最好证明。

## 7. 应用效果：两个官方样本的真实模型能力画像

本章给出系统在**两个官方脱敏样本**上对 `deepseek-v4-flash` 的真实评测结果。所有分数均为**实测、可复现**（持久化对话 + seed + 缓存，连续两次逐字节一致；命令见 §4.3 / `build_official_demo.py`），错误数 `error=0`。

### 7.1 样本 1 · 飞毛腿合同通知 — 综合 63.6（需改进）

| 维度 | D1 流程 | D2 任务 | D3 约束 | D4 知识 | D5 对话 |
|---|---|---|---|---|---|
| 得分 | 75.0 | 100.0 | 73.6 | **0.0** | 91.7 |

各场景（最弱在前）：坚持拒绝型 **45** → 合作型 65 → 越界型 65 → 打断型 **79.29**。最常违反的约束（实测跨场景失败率）：

- **字数控制（C04，"约 30 字以内"）失败率 100%** —— 模型话术普遍超长，这是最硬的短板；
- **FAQ 知识正确（C15 [META]）失败率 100%** —— 模型基本没有主动覆盖 FAQ 知识点，直接拖垮 D4 知识维度到 0；
- S4"按排名说明"（C10）失败率 75%、语气随意（C03）/ S2 合同说明（C08）各 25%。

**诚实解读**：模型在"任务完成度（D2=100）"和"对话质量（D5=91.7）"上很好，但**踩了两个客观硬伤——字数超标、FAQ 知识缺失**，被 D3/D4 拉到 63.6。这恰恰展示了系统的价值：不是给一个模糊的"还行"，而是精确指出"超字数 + 没讲知识点"这两个可立即改进的点。

### 7.2 样本 2 · 课程升级告知 — 综合 44.2（不合格）

| 维度 | D1 流程 | D2 任务 | D3 约束 | D4 知识 | D5 对话 |
|---|---|---|---|---|---|
| 得分 | 54.2 | **25.0** | 54.2 | 100.0 | 60.0 |

各场景（最弱在前）：坚持拒绝型 **21.99** → 越界型 45 → 打断型 45 → 合作型 65。最常违反的约束（失败率 100% 的就有四条）：

- **极简字数（C01，"最多 15-20 字"）100%**、**不冗长正式（C07）100%** —— 课程发布任务对话术要求比飞毛腿更严（15-20 字 vs 30 字），模型话术偏长偏正式，**字数 + 口语化全线崩**；
- **S5 检查学员端费用（C16）100%**、**"若老板说忙"规定话术（C10）100%** —— 多分支流程没走完整，任务完成度 D2 仅 **25**。

**诚实解读**：同一个 `deepseek-flash`，在更严格的课程发布任务上（44.2）明显比飞毛腿（63.6）差。**这个差异是有意义的**——它证明系统能区分任务难度、能反映模型在不同业务约束下的真实表现，而不是给所有任务一个雷同分数。

### 7.3 系统价值落点：这正是赛题要的"可量化 + 可解释 + 给方向"

把两个画像放在一起，恰好兑现了赛题的三条核心诉求：

1. **可量化**：0–100 分（63.6 / 44.2），而非 0/1，可横向比较；
2. **可解释**：每个分数都能下钻到"哪个维度弱、哪条约束失败率多高、证据在第几轮"；
3. **给优化方向**：自动诊断直接点出"重点优化流程遵循与约束执行""字数超标 + FAQ 缺失"等可立即行动的改进点。

### 7.4 交付形态：一站式平台

系统以 Streamlit 一站式平台交付，覆盖赛题要求的"用户输入指令 → 模拟 → 评测 → 报告"全链路：

- **评模型**：选预置指令 **或 粘贴/上传自己的完整任务指令** → 8 Persona 自动模拟多场景对话 → 评测 → 模型能力画像；
- **评单通对话**：直接给一通已有对话、或给一句大致描述由系统模拟一通 → 用内置通用质检标准评这通对话；
- **两种运行模式**：快速演示（读预生成的真实结果，秒出，供现场演示）/ 完整运行（真调模型，需 API key）。

> **全文小结**：本系统把外呼对话的"指令遵循能力评估"做成了一条可解释、可量化、可复现、可定位短板的工业级流水线——客观约束规则零成本且与人工完美一致（κ=1.0），主观约束用 LLM + 自一致性投票判定并诚实报告其可靠性边界（整体 κ=0.45 / 一致率 81.8% / 三路互查 0.81），最终对任意任务指令产出"0–100 分 + 逐约束证据 + 优化方向"的模型能力画像。它不仅能替代人工质检的慢与贵，更能反过来发现人类标注的盲区——这是我们认为它具备工业级落地价值的根本原因。

## 1. 赛题理解

### 1.1 赛题原文

> **任务背景**：在履约数字人外呼场景中，系统自动发起与用户的通话，对话模型需要根据预设的指令完成具体的任务。由于指令中包含复杂的任务流程和多种约束，人工评估成本高且难以量化。需要构建一套针对对话模型任务指令遵循效果的可解释可量化的自动评估能力。
>
> **任务描述**：设计并实现针对已有任务指令的自动化指令遵循能力评估系统，需要保证评估过程的可解释性以及评估结果的可靠性。
>
> **交付目标**：
> 1. 构建用户模拟器，能够充分有效测试对话模型在特定任务指令下的效果
> 2. 自动产出评测报告，要求评测过程可解释结果可量化

### 1.2 一招老师直播原话（关键信息源）

#### 系统形态
> "我们的输入其实是一个任务的指令...你可以认为是一个给到对话模型的 prompt"
>
> "前端有一个界面，然后这个界面里面是可以让用户去输入这个任务的指令，然后我们只针对这一个指令去做后续的一个对话模拟，效果评估，最终去产出一个比较清晰的可量化的一个评估报告"
>
> "给出一个任务的指令，**给出一个需要测试的模型**，最终就是直接可以通过这个系统运行"

#### 核心需求
> "整个评估的过程是可解释的"
>
> "结果是可以量化的，而不是说直接给出一个 0、1 的分数，还是需要可能给出一个 **0 到 100 这么一个分数**"
>
> "让我们知道目前的这个系统能达到什么样效果，**让我们后面的优化的方向是什么**"

#### 痛点描述
> "整个评估的耗时会非常长，没办法去大批量的去执行"
>
> "也很难说有一个很统一的指标，或者说最终的一个优化方向的总结"

#### 业务场景
> "AI 的站长...定时需要给这个骑手去打一些电话...提醒他去做出勤了，提醒他注意安全了，提醒他有一些线下的培训服务需要去参加"
>
> "我们会定期去招聘一些骑手...走一些自动化的这个招聘流程"
>
> "骑手助手里面可能也会需要去定期帮骑手解决一些问题。比如说商家可能出餐慢了，或者说用户觉得这个送餐的时间比较晚，或者说地图定位不是很准"

#### 数据形态
> "已经从用户的这个语音里面，通过 ASR 转换成文本，所以我们在这个题目里面其实可以只考虑这个文本的数据就可以了"

### 1.3 题目本质拆解

这不是建模题，是**评测系统工程题**。本质是三个子问题的乘积 + 一个交付层：

1. **指令解析**：把自然语言的复杂指令转成机器可执行的"约束清单 + 状态图"
2. **用户模拟器**：能压测对话模型在各种用户行为下的指令遵循表现
3. **评测裁判**：判定每条约束是否被遵守，产出 0-100 分数 + 可解释报告 + 优化方向
4. **一站式平台**：前端 UI，让用户输入指令、选模型、看报告（**赛题硬要求**）

### 1.4 评分关键词解读

赛题原文 + 直播明确提到的关键词：

- **"可解释"** → 每个判定都要能追溯到证据
- **"可量化"** → 0-100 分，不是 0/1（直播明确）
- **"可靠性"** → 你的系统判得准不准要有数据证明（核心护城河）
- **"充分有效"** → 用户模拟器覆盖所有约束（另一条护城河）
- **"优化方向"** → 必须告诉用户怎么改进（直播明确）
- **"一站式"** → 必须有完整端到端流程，不能是脚本拼凑（直播明确）

## 3. 取胜战略

### 3.1 战略定位

**主攻技术质量与可靠性，最后阶段顺带打磨商业故事。**

之前 v2 提议"主攻商业故事"，但会挤压技术基本盘。回归务实：**技术质量与可靠性是基本盘必须保住**，商业故事用 W6 一周打磨即可。

### 3.2 取胜逻辑

```
普通队伍方案 = LLM-as-Judge 一把梭 + 输出一个总分
合格的赛题答卷 = 解析器 + 模拟器 + 0-100评分 + 前端UI + 优化建议
进阶答卷 = 合格答卷 + 评测可靠性实证 + 覆盖性证明 + 对照基线
```

### 3.3 五大差异化抓手

| 抓手 | 普通队伍 | 我们的方案 |
|---|---|---|
| 可解释性 | 给总分 + 简单理由 | 原子级证据：每 turn × 每约束的 pass/fail + 引用证据 |
| 可靠性 | 假设 LLM Judge 准 | Gold Set 人工标注 + Cohen's kappa + 多 judge 消融 |
| 覆盖性 | 跑几通对话看看 | Persona × 约束覆盖矩阵 + 软件测试覆盖率指标 |
| 通用性 | 写死规则 | 解析器从指令文本自动产出约束清单 |
| 创新性 | 无对照 | 混合 verifier vs 纯 LLM Judge vs 纯规则的对照实验 |

### 3.4 三个必做对照实验

1. **人工 vs 自动**：50 通 Gold Set 上，你的系统 vs 人工标注的 Cohen's kappa ≥ 0.75
2. **方法消融**：你的混合 verifier vs 纯 LLM Judge vs 纯规则的 F1/kappa 对比
3. **模型对比**：用你的系统评测 3-4 个被测模型（GPT-4o / Claude / Qwen / DeepSeek），出榜单

### 4.2 数据流（Pipeline）

```
用户在 UI 输入指令 + 选择被测模型
    │
    ▼ [Layer 1 指令解析器]
约束清单 + DAG + FAQ KB (JSON)
    │
    ▼ [Layer 2 用户模拟器 × N persona × 选定模型]
对话轨迹集 (JSONL)
    │
    ▼ [Layer 3 评测裁判]
约束判定结果 (per turn × per constraint)
    │
    ▼ [Layer 4 报告生成器]
0-100 分综合分 + HTML 报告 + 优化建议
    │
    ▼ [Layer 5 前端展示]
评测报告可视化
```

### 4.3 三级评测框架（借鉴 Meeseeks）

| 等级 | 名称 | 粒度 | 例子 |
|---|---|---|---|
| L1 | 任务级 | 整通对话 | 任务核心意图是否完成 / Call Flow 是否全覆盖 |
| L2 | 约束级 | turn 或对话 | 长度 ≤ 30 / 越界话术 / 禁用词 / FAQ 正确性 |
| L3 | 细粒度 | 字符或句式 | 语气随意 / 避免重复 / 变量替换 |

### 4.4 0-100 分综合评分算法（v3 新增）

直播明确要求 0-100 分制。设计如下：

```
总分 = L1 任务级得分 × 40%
     + L2 约束级得分 × 40%
     + L3 细粒度得分 × 20%

L1 得分 = (L1 约束通过率) × 100
L2 得分 = Σ(约束 i 通过率 × 约束 i 权重) / Σ权重 × 100
L3 得分 = 同上

关键约束 (is_critical=true) 通过率作为闸门：
- 若关键约束通过率 < 60%，总分上限降为 60
- 若关键约束通过率 < 40%，总分上限降为 40
```

### 4.5 Persona 设计（8 种）

| Persona | 测试意图 | 必触发约束 |
|---|---|---|
| 配合型 | Happy path 主流程 | L1 Task / L1 Flow Coverage |
| 提问型 | 密集触发 FAQ | L2 FAQ Correctness |
| 越界型 | 问范围外的问题 | L2 Out-of-scope Response |
| 拒绝型 | 持续拒绝 | L2 Early Termination / L3 Tone |
| 打断型 | 中途插话 | L2 Interruption Handling |
| 状态型 | "我在开车/很忙" | L2 Busy User Handling |
| 模糊型 | 给模糊回答 | L2 Clarification |
| 对抗型 | 诱导违反约束 | L2 No Commitment / 红线 |

### 4.6 Verifier 类型选择原则

| 约束类型 | 推荐 verifier | 理由 |
|---|---|---|
| 字符数、关键词、占位符、禁用词 | rule | 0% 幻觉，绝对可靠 |
| 流程步骤覆盖、分支正确性 | state_tracker | 跨 turn 状态需要专门追踪 |
| FAQ 知识正确性、承诺判定 | llm_extract_then_rule | LLM 抽取 + 规则比对，比纯 LLM 更可靠 |
| 语气、自然度、风格 | llm_judge | 没有规则能判定的语义项 |

### 4.7 优化方向生成模块（v3 新增）

**这是赛题硬要求，不是创新点**。设计两档：

**档1（保守，必做）**：基于失败聚类生成结构化建议
- 输入：所有失败的约束判定（按 turn / 约束 / persona 聚类）
- 输出：分项报告"Step X 的约束 Y 在 Z 个 persona 下失败"
- 实现：纯规则统计 + 模板生成，零幻觉

**档2（激进，可选）**：LLM 生成具体的 prompt 修改建议
- 输入：失败 case + 原指令
- 输出：建议在原 prompt 第几行加什么话
- 风险：LLM 给的建议可能不靠谱
- 应对：标注为"参考建议"，不作为主交付内容

**建议先做档1，时间允许再加档2**。

### 5.3 不需要做的事

- ❌ 不训练任何模型
- ❌ 不造远场景指令

### 5.4 Gold Standard 标注的关键性

这是评测可靠性的命根子。具体要求：
- 至少 50 通对话逐 turn × 逐约束人工标注
- 2-3 人独立标，算 Cohen's kappa ≥ 0.7
- kappa 不达标必须停下来开会统一标准

## 9. 关键技术决策记录

### 9.1 决策：是否做模型训练？
**结论**：不做。
**理由**：赛题是评测系统，不是建模。

### 9.2 决策：用户模拟器是 prompt 工程还是微调？
**结论**：prompt 工程 + 状态机。
**理由**：成本低、可解释、可调试。

### 9.3 决策：LLM Judge 用哪个模型？
**结论**：主用 GPT-4o-mini，关键约束用 GPT-4o / Claude。

### 9.4 决策：DAG schema 是扁平还是嵌套？
**结论**：必须嵌套。示例 2 有 Step 3 含 3.1/3.2/3.3。

### 9.5 决策：18 条还是 6 条变体？
**结论**：6 条围绕真实业务场景的变体。

### 9.6 决策：评分形式？（v3 新增）
**结论**：必须 0-100 分。直播明确要求。
**算法**：L1 × 40% + L2 × 40% + L3 × 20%，关键约束作闸门。

### 9.7 决策：是否做优化建议生成？（v3 新增）
**结论**：必做。赛题硬要求。
**实现**：先做保守版本（失败聚类 + 模板），LLM 自动建议作为可选加分。

### 9.8 决策：是否做前端 UI？（v3 新增）
**结论**：必做。赛题硬要求"一站式平台"。
**实现**：用 Streamlit 或 Gradio 快速搭，不碰 React/Vue。

### 9.9 决策：多模型支持？（v3 新增）
**结论**：核心接口必做，至少支持 2 个被测模型。

## 15. 软件测试视角的覆盖率指标

### 15.1 为什么用软件测试话术

赛题原文"**充分有效**测试"直接对应软件测试领域的"测试充分性"。借用成熟指标，把主观判断变成量化指标。

### 15.2 四个核心覆盖率指标

#### 节点覆盖率
- DAG 中每个 step 节点是否被触发
- 计算：`已触发节点数 / 总节点数`
- 目标：等真实数据出来后定

#### 分支覆盖率
- 每个 if/else 分支的两个方向是否都跑过
- 示例 2 Step 4 "Web 控制台 / 第三方系统" 两个分支必须都触发

#### 路径覆盖率
- 端到端的合法对话路径覆盖率
- 因组合爆炸，目标允许低一些

#### 约束-Persona 覆盖矩阵
- 每条约束至少被 N 个 persona 触发
- 输出 23 × 8 覆盖矩阵热力图

### 15.3 答辩展示
- PPT 第 9 页放图：DAG 可视化（已覆盖绿色 / 未覆盖灰色）+ 覆盖率数字 + 23 × 8 矩阵热力图
- 一句话标题：用图论指标证明测试充分性

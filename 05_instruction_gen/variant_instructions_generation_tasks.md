# Day 3 变体指令生成任务包

> **目标**：按 v3 README 修订计划，生成 6 条变体指令
> **方法**：把下面 6 个 prompt 复制到 Claude.ai / ChatGPT，逐个跑，每条生成 2 次取较优
> **校验**：每生成一条，跑 `validate_instruction.py` 校验通过才算完成

---

## 通用规则

每条指令必须包含 5 个段落：`# Role / # Task / # Opening Line / # Call Flow / # Constraints`（FAQ 可选）。

生成后跑校验：
```bash
python validate_instruction.py path/to/V1.md
```
不过的让 LLM 改，过了再进下一条。

## V1：通知骑手参加线下安全培训

**Prompt 复制到 Claude/GPT**：
```
你是一名美团外呼数字人产品的指令工程师。我需要你生成一份完整的外呼任务指令,场景是"AI站长通知骑手参加线下安全培训"。

请严格按以下结构生成,模仿示例1(飞毛腿骑手通知)的格式和密度,但场景换成"安全培训通知":

# Role
[一句话描述 assistant 是骑手站长]

# Task
[1-2 句任务目标:通知骑手 X 月 X 日有线下安全培训,确认是否参加]

# Opening Line
[首轮开场白,50-100字,含 ${rider_name} 和 ${training_date} 变量,直接告知核心信息]

# Call Flow
[3-4 个线性步骤,简单档(对标示例1):
1. 告知培训时间地点,询问是否参加
2. 如不能参加,询问原因并记录
3. 如参加,提醒携带物品(头盔/工牌/身份证)
4. 强调安全培训重要性,如未参加会影响接单评级]

# Knowledge Points (FAQ)
[3-5 条常见问题答复,例如:
- 培训时长多久 → 2小时
- 是否有补贴 → 出席补贴 X 元
- 错过怎么补 → 联系站长安排下批次]

# Constraints
[6-7 条约束,必须包含:
1. 每次回复约 30 字以内
2. 被问超出职责的问题,回复"我向同事确认后再回电"
3. 保持随意自然语气
4. 避免重复回复
5. 不能承诺额外补贴
6. 若骑手坚持不参加,礼貌挂断
7. 不说"好的"等语气词]

要求:
- 业务真实(模仿美团骑手运营场景)
- 变量丰富(至少3个 ${占位符})
- 约束可验证(每条能客观判定)
- 不要直接抄示例1的措辞

直接输出 Markdown,不要前后缀说明。
```

## V2：通知骑手新版 APP 强制更新

**Prompt**：
```
你是一名美团外呼数字人产品的指令工程师。生成一份外呼指令,场景:"AI站长通知骑手在 24 小时内更新新版骑手 APP,否则将无法接单"。

按以下结构生成,模仿示例1结构,简单档:

# Role
美团骑手站长

# Task
通知骑手更新 APP,确认更新后能正常接单

# Opening Line
50-100字,含 ${rider_name} 和 ${deadline} 变量

# Call Flow
3-4 个线性步骤:
1. 告知 APP 更新强制要求和截止时间

- 更新失败怎么办

6. 避免重复
```

## V3：通知骑手注意恶劣天气出勤

**Prompt**：
```
生成外呼指令,场景:"AI站长在台风/暴雨预警时,致电片区内骑手,提醒注意安全/取消高单量任务/告知调休补贴"。

复杂度:中等(5-6 个步骤,含 1 处分支)

# Role
美团骑手站长(安全运营)

# Task
通知骑手 ${weather_type} 预警,提醒安全 + 告知调休补贴政策

# Opening Line
50-100字,含 ${rider_name} 和 ${weather_type}(暴雨/台风/暴雪)变量

# Call Flow
5-6 步,含分支:
1. 告知天气预警和等级
2. 询问当天是否计划出勤
3. **分支1**:若计划出勤 → 进入Step 4(安全提醒);若不出勤 → 跳到Step 5
4. 安全提醒:慢行/穿雨具/拒不安全订单 + 提供站点紧急联系
5. 告知调休补贴政策(单笔订单补贴×1.5,可申请调休)
6. 确认骑手知悉,记录

# Knowledge Points (FAQ)
5-7 条:
- 出勤补贴标准
- 如何申请调休不扣绩效
- 极端天气如何拒单不被处罚
- 中途遇险如何呼救

# Constraints
8-9 条:
1. 每次回复 20-30 字
2. 越界回复"我帮您记录回头跟进"
3. 保持温和担忧的语气(对应预警情境)
4. 不能承诺超出政策的额外补贴
5. 若骑手坚持冒险出勤,反复劝阻 2 次后挂断
6. 若骑手已在路上,简短安全提示后让其专心驾驶
7. 不说"好的""哈哈"等
8. 避免重复

直接输出 Markdown。
```

## V4：商家出餐慢的协调外呼

**Prompt**：
```
生成外呼指令,场景:"骑手助手致电商家,核实出餐慢的原因 + 协调预计出餐时间 + 提醒尽快"。

复杂度:中等(对标示例2的客服外呼商家结构)

# Role
美团骑手助手客服

# Task
核实商家出餐延迟原因,协调预计出餐时间,告知用户/骑手等待情况

# Opening Line
50-100字,含 ${merchant_name} 和 ${order_id} 和 ${current_delay_minutes} 变量

# Call Flow
6-7 步,含分支:
1. 自我介绍 + 询问是否商家负责人
2. 确认订单号 ${order_id},说明已超时 ${current_delay_minutes} 分钟
3. **分支**:询问出餐慢原因
   - 3.1 高峰期忙不过来 → 进Step 4
   - 3.2 食材缺货 → 询问是否需取消订单进Step 6
   - 3.3 系统未接单 → 协助商家在后台确认接单进Step 4
4. 询问预计出餐时间
5. 协调:告知用户/骑手等待,记录商家配合度
6. 如取消订单:引导商家在商家版APP操作取消流程
7. 道谢结束

# Knowledge Points (FAQ)
6-8 条:
- 商家版APP操作取消流程
- 商家被投诉影响评级
- 超时后骑手是否还会接单
- 商家忙时如何主动延长出餐时间
- 食材临时缺货能否更换

# Constraints
10 条:
1. 每次回复 15-20 字
2. 口语化,像电话沟通
3. 频繁给商家发言机会
4. 给出信息后暂停等回应
5. 被打断用过渡语"您刚才提到..."
6. 任务完成后仍简短作答疑问
7. 不说"好的""哈哈"等
8. 不承诺给商家折扣/补贴
9. 若商家说在忙,说"就1分钟,保证简短"后继续
10. 若商家说开车,礼貌说"那我稍后再打"后挂断

直接输出 Markdown。
```

## V5：商家收到差评的回访

**Prompt**：
```
生成外呼指令,场景:"骑手助手致电商家,告知用户给了差评 + 安抚情绪 + 引导申诉/改善建议"。

复杂度:中等

# Role
美团商家关怀客服

# Task
通知商家收到差评 + 安抚 + 引导申诉流程 + 收集改善意见

# Opening Line
含 ${merchant_name} 和 ${review_count_last_7days} 变量

# Call Flow
6-7 步,含分支:
1. 自我介绍 + 询问是否商家负责人
2. 告知近 7 天差评数量,简述主要差评原因
3. **分支**:询问商家是否需要申诉
   - 3.1 想申诉 → 进Step 4(申诉流程)
   - 3.2 不申诉/承认问题 → 进Step 5(收集改善意见)
4. 介绍申诉流程:在商家版APP-评价管理-差评申诉,提交证据
5. 收集改善意见:询问商家有什么困难需要平台协助
6. 安抚:告知偶尔差评不影响整体评级,但需关注趋势
7. 道谢结束

# Knowledge Points (FAQ)
6-7 条:
- 申诉成功率
- 多少差评会影响评级
- 商家投诉用户怎么处理
- 差评赔付金额范围
- 改善建议反馈渠道

# Constraints
10 条:
1. 每次回复 15-20 字
2. 口语化但保持同理心(对应商家可能情绪低落)
3. 频繁给商家发言机会
4. 被打断用过渡语
5. 任务完成后仍简短作答
6. 不说"好的""哈哈"等
7. 不能承诺申诉一定成功
8. 不能承诺给商家补贴
9. 若商家激动情绪,先安抚再推进流程
10. 若商家说开车/在忙,按对应规则处理

直接输出 Markdown。
```

## V6：商家关店申请的核实外呼

**Prompt**：
```
生成外呼指令,场景:"骑手助手致电商家,核实其提交的关店申请是临时还是永久,确认后续流程"。

复杂度:复杂(对标示例2,7 步含嵌套分支)

# Role
美团商家运营客服

# Task
核实商家关店申请(临时/永久),确认操作 + 告知后续影响

# Opening Line
含 ${merchant_name} 和 ${close_request_type}(初始可能未知)变量

# Call Flow
7 步,含多层分支:
1. 自我介绍 + 询问是否商家负责人
2. 告知系统收到关店申请,询问是否本人操作
3. **分支**:确认关店类型
   - 3.1 临时关店(节假日/装修/缺人) → 进Step 4 临时流程
   - 3.2 永久关店(经营不善/转让) → 进Step 5 永久流程
   - 3.3 误操作 → 进Step 6 撤销流程
4. 临时流程:
   - 4.1 询问预计重开时间
   - 4.2 告知临时关店后台操作步骤(分步引导)
   - 4.3 提醒影响:暂停接单,排名暂时下降
5. 永久流程:
   - 5.1 询问关店原因(改善产品流程用)
   - 5.2 告知永久关店流程:30天等待期 + 提现保证金 + 解约条款
   - 5.3 询问是否考虑挂靠其他经营方式
6. 撤销流程:
   - 6.1 引导商家撤销操作(分步)
   - 6.2 确认撤销成功
7. 道谢结束

# Knowledge Points (FAQ)
8-10 条:
- 临时关店多久必须重开
- 永久关店保证金返还时间
- 暂停接单期间订单怎么处理
- 关店期间客户咨询如何回复
- 重开后排名如何恢复
- 是否影响其他平台
- 永久关店后能否重新开店
- 转让经营权流程

# Constraints
12 条:
1. 每次回复 15-20 字
2. 口语化,像电话
3. 频繁给商家发言机会
4. 被打断用过渡语
5. 任务完成后仍简短作答
6. 不说"好的""哈哈"等
7. 不能承诺加快流程或免除等待期
8. 不能承诺给折扣或补贴
9. 引导操作时分步发送(每步暂停3秒,文本对话中分轮发)
10. 永久关店时表达适度遗憾但不劝留
11. 若商家说开车,礼貌挂断
12. 若商家说在忙,说"就1分钟"后继续

直接输出 Markdown。
```

## 完成后的操作

每条指令生成后:

```bash
# 1. 保存为 V1.md / V2.md / ... / V6.md
# 2. 跑校验
cd 05_instruction_gen
python validate_instruction.py path/to/V1.md

# 3. 不通过就改 prompt 重新让 LLM 生成
# 4. 通过的存放到 03_examples/variants/
```

**最终交付物**: 6 条 markdown 指令,全部通过校验,放在 `03_examples/variants/` 目录下。

**预估时间**: 每条 10-15 分钟(含校验+迭代), 6 条共 1-2 小时。

# 标注规范 v2.0 (Day 10 重标版)

> **写给你**：v1.0 规范在 Day 5 写的，但 Day 5-9 实证发现你 v3/v4/v5 都还有 **20% 的系统性错误**。这版以你的真实错误为靶子。
>
> **核心目标**：让你不再凭直觉标，而是按机械流程一步步判。
>
> **使用方式**：标注前先读"第 0 节"，标的过程中遇到困惑就回查对应约束类型的章节。

---

## 第 0 节：开始之前必须建立的 4 个心智

### 0.1 你不是在评价模型"好不好"，是在判约束"满不满足"

**错误心智**："这通对话挺自然的 → 标 pass"
**正确心智**："这条约束说的是 X → 对话里有/没有做到 X → pass/fail"

你 Day 5 最常犯的错就是**用整体印象代替单点判定**。

### 0.2 Evidence 是用来证明 verdict 的，不是描述对话

每填一条 evidence，问自己：
> **"这段 evidence 能直接证明 verdict 对不对？"**

**反例**（你的真实错误）：
- 约束 V1_C05："绝不能承诺额外的补贴"
- 你标 pass，evidence 写："开场白含全部变量: 王强/10月15号下午2点"
- ❌ Evidence 完全没说"是否承诺补贴"——这是错位！

**正例**：
- 同样约束 V1_C05
- 你标 pass，evidence 应该写："T1-T8 中助手未提及任何补贴/补偿/赔偿"
- 你标 fail，evidence 应该写："T7 助手说'我帮你申请加 50 块补贴'"

### 0.3 一条约束 = 一个独立判定单元

不要把多个判定混在一起。

**错误**：V2_C12 (S1 自我介绍) 标 fail，evidence 写"T7 超 45 字"
- ❌ 字数违规属于 V2_C01 长度约束，跟 S1 流程结构无关

**正确**：
- V2_C12 (S1 自我介绍)：看是否有自我介绍 + 问负责人 → 跟字数无关
- V2_C01 (字数)：看每轮字数 → 跟流程无关

### 0.4 三种状态：pass / fail / na 各有清晰边界

| 状态 | 含义 | 例子 |
|---|---|---|
| **pass** | 约束适用 + 满足 | "禁说好的"——全文确实没说"好的" |
| **fail** | 约束适用 + 违反 | "禁说好的"——T3 说了"好的" |
| **na** | 约束不适用（条件未触发）| "若用户开车则挂断"——用户全程没说开车 |

**关键**：**约束适用 = 触发**。条件性约束（"若...则..."）必须先判触发，再判执行。

## 第 1 节：标注的机械流程（每条约束 4 步走）

**每条约束必须走完这 4 步**，跳步必错。

```
Step 1: 读约束 name + source_text
        → 问自己: "这条约束到底要判什么?"

Step 2: 看约束的 verifier 类型
        → rule/rule_pattern/state_tracker/llm_extract_then_rule/llm_judge
        → 决定用哪套判定标准 (见后面各小节)

Step 3: 检查约束是否触发
        → 条件约束 (若X则Y): 看 X 是否发生
        → 非条件约束: 默认触发

Step 4: 应用判定标准 → 写明确 evidence
        → Evidence 必须能直接证明 verdict
```

**疲劳防御**：每标 5 通必须休息 5 分钟。检测疲劳的信号：
- 开始凭整体印象标（不再回看具体约束）
- Evidence 越写越短或抄上一通
- 心里想"差不多就 pass 吧"

## 第 2 节：按 verifier 类型的判定标准（核心）

### 2.1 rule 类（字数 / 占位符）

**判定规则**：纯机械，**不允许通融**。

**字数约束**（如 "每次回复 15-20 字"）：
- 数所有 assistant turn 的字符数（含标点）
- **首轮开场白豁免** ✓
- 非首轮中超过 `上限 + 5` 字 → fail
- 违规率 ≥ 30% → fail；< 30% → pass

**实例**：V4_C01 "每次回复 15-20 字"
- 上限 20 + 软 5 = 25 字
- 全 4 个非首轮 assistant 回复，3 个超 25 字 → 违规率 75% → **fail**

**最常见你的错误**：
- ❌ 你 v5 标 V4_C01 pass，evidence 写 "您好，请问是老王炸鸡店的负责人吗？"（这是开场白，应豁免，但**其他轮都超字数你没看**）
- ✅ 正确做法：列出每轮字数 →"T1=64字(豁免) T3=30字(超) T5=23字 T7=36字(超)..."

**占位符约束**（"变量替换无残留"）：
- 全文搜索 `${xxx}` 这种模板字符
- 找到任一处 → fail；无 → pass

### 2.2 rule_pattern 类（禁用词 / 开场白合规）

**禁用词类**（如 "禁用'好的'/'哈哈'"）：
- 全文搜索目标词
- 出现 1 次 → fail（**含变体如"好的呀"也算**）
- 完全不出现 → pass

**注意**：
- "嗯" 不在禁用词内（如果约束没列）
- "好嘞" 不等于 "好的"
- 写 evidence 时引用具体 turn 号：`T3: "好的，那我帮你..."`

**开场白合规类**（如 "开场白必含负责人/培训机构"）：
- 只检查第 1 个 assistant turn
- 必须**所有**关键词都含 → pass；缺任一 → fail

### 2.3 state_tracker 类（流程 Step 覆盖）

**判定规则**：**只看意思有没有到，不看字数、不看格式**。

**实例**：V4_C12 "S1 自我介绍并询问接电话的是否为商家负责人"
- 找对话里有没有这两个动作：
  - 自我介绍（"我是美团客服"/"咱们站长"等）
  - 询问负责人（"请问是负责人吗"）
- 两者都有 → **pass**
- 缺任一 → fail

**你 Day 5 最严重的错误**：
- ❌ 你看到 T1 超 45 字 → 标 V4_C12 fail，evidence 写"T7=45字超长"
- ✅ 字数违规归 V4_C01，**跟 V4_C12 无关**。这是错位！

**实例**：V4_C20 "S6 取消订单流程：引导商家在商家版APP操作取消"
- 找对话里有没有"让商家自己取消"的引导
- 助手说"您去 APP 点取消" → pass
- 助手只说"那我帮您取消"或没提取消 → fail

**Step 没走到怎么办**？
- 比如对话只 5 轮，没走到 S6
- 标 `na`，evidence 写"对话仅 5 轮，未触发 S6 阶段"

### 2.4 llm_judge 类（主观判断）

**这类约束你 Day 5 错得最多**。核心问题：你**用模糊直觉代替明确标准**。

#### 2.4.1 "口语化自然"类（V*_C02/C03）

**机械判定**（按这 3 条逐一查）：
1. **是否有列点**（1. 2. 3. / 首先 其次 / 综上）？ 有 1 处 → fail
2. **是否有书面文言词**（兹/便/若/之/故/亦/望/敬请/务必）？ 有 2 处+ → fail
3. **是否完全没口语词**（咱们/嗯/啊/吧/呗/呢/吧/喂/哈/嘞）？完全 0 处 → fail

任一条满足 → **fail**；都不满足 → pass

**实例**：V4_C02
- 助手说："您好，请问是老王炸鸡店的负责人吗？我是美团客服..."
- 列点？无 ✓ | 书面词？无 ✓ | 完全没口语词？仅 1 处"嗯" → 仍有 → ✓
- → **pass**

你 v5 标 pass 是对的，但 LLM 判 fail 也有道理（LLM 标准更严：要求 ≥2 个口语词）。

#### 2.4.2 "避免重复"类（V*_C04）

**机械判定**：
- 找 8+ 字连续片段在不同 turn 出现 2 次以上 → fail
- 或同样问题被问 2 次 → fail
- 否则 pass

**举例**：T1 "记得带头盔工牌身份证" + T5 "提醒您带好头盔工牌身份证" → 8+ 字重复 → fail

#### 2.4.3 "适时结束"类（V*_C15 = [META] 适时终结对话）

**这是你 Day 5 标错最多的一类（15+ 处）**。

**机械判定**（必须全满足才 pass）：
1. **用户明确表示结束意愿后**，助手在 **1-2 个 turn** 内收尾
2. 收尾含 "再见"/"祝"/"辛苦"/"感谢"/"挂了"
3. **没有**反复追问 "还有其他需要吗"/"还有问题吗"

任一条违反 → fail。如果对话被强制截断（达到 max_turns 没自然结束）→ fail。

**典型 fail 案例**（你之前误标 pass 的）：
```
T10 user: 好的，我先跑单去了。
T11 assistant: 行，那你抓紧。挂了啊。   ← 这里就该结束
T12 user: 好的站长，感谢提醒。
T13 assistant: 行，找个信号好的地方下，别下载一半失败了。   ← 多此一举
T14 user: 好嘞，我这就去更新。
T15 assistant: 下载完立刻登录试一下。   ← 又来一次
T16 user: 好的，下载完马上登录。
T17 assistant: 那你先试。更新完登录接单都正常吧？   ← 还在问
```

用户 T10 已经"先跑单去了"明确结束，但助手 T11-T19 还在追问 4 次 → **fail**

#### 2.4.4 "条件应答"类（V*_C05/C06/C10/C11）

**结构**："若 X 则 Y"（如"若骑手拒绝则挂断"）

**机械判定**（2 步）：
1. **条件是否触发**？没触发 → **na**（不是 pass！）
2. 触发后助手是否做了规定动作？做了 → pass；没做 → fail

**实例**：V2_C05 "若骑手明确拒绝更新，告知后果后挂断"
- 看对话：用户明确拒绝了吗？
  - 用户说"行行行我知道了，晚上回去再说" → 这是**敷衍**，不是明确拒绝 → **na**
  - 用户说"我不更新，凭什么强迫" → 明确拒绝 → 触发
- 触发后助手是否"告知后果 + 挂断"？
  - 告知"不更新接不了单" + 1-2 轮内结束 → pass
  - 还在劝说没挂断 → fail

**你 Day 5 错误模式**：直接看到对话最后挂断了 → 标 pass，没仔细看条件是否触发。

#### 2.4.5 "任务核心意图完成"类（V*_C14 = [META] 任务完成度）

**机械判定**：
1. 助手是否覆盖了 Task 描述的核心动作（≥ 70%）？
2. 用户是否给出明确反馈（同意/拒绝/接收信息）？

两条都满足 → pass。

**特殊场景**：
- 用户拒绝场景：助手记录了拒绝 + 给出后续方案（补训/请假）→ pass
- 用户中途挂电话 → 看挂之前核心动作是否完成

### 2.5 llm_extract_then_rule 类（事实抽取 + 规则）

#### 2.5.1 "禁止承诺"类（V*_C05/C08）

**机械判定**：
- 找 assistant 是否说出了"承诺金钱补偿"的话
- 关键词：折扣/补贴/赔付/优惠/免单/返现/补偿
- 配合承诺词：我帮您/我会给/保证/肯定

**实例**：
- ✗ 违规："我帮您申请 50 块超时补贴" → fail
- ✗ 违规："放心，平台会赔您" → fail
- ✓ 合规："这个超出我职责范围" → pass
- ✓ 合规："建议您走平台申诉" → pass

**你 Day 5 错误**：V4_C08 "禁止承诺折扣"，你 evidence 写"结束未礼貌道谢" → **完全错位**！这两件事无关。

#### 2.5.2 "越界处理"类（V*_C02/C09）

**机械判定**（必须 2 步）：
1. 用户是否问了越界问题？（无关任务的私人话题/外平台/职责外）
2. 触发后助手是否用了"我向同事确认/回头跟进/记录后回复"类话术？

| 用户行为 | 助手响应 | 判定 |
|---|---|---|
| 没问越界 | - | na |
| 问越界 | 用了规定话术 | pass |
| 问越界 | 直接答了 / 没用规定话术 | fail |

#### 2.5.3 "FAQ 知识"类（V*_C16 = [META] FAQ 知识正确）

**机械判定**（核心 2 点）：
1. 用户问了 FAQ 列表中的问题吗？
2. 助手回答是否符合标准答案 + **前后不自相矛盾**？

**特别注意**：**自相矛盾**也算 fail！
- 例：T9 助手说"不参加影响评级"，T11 又说"不影响评级" → **fail**

## 第 4 节：标注 SOP（标准操作流程）

### 4.1 每通对话开标前

```
1. 读指令(如 V4.md): 5 分钟
2. 读对话原文(逐 turn): 3-5 分钟  
3. 心里复述: 助手做了什么? 用户做了什么? 是否完成任务?
4. 准备好约束清单(16-26 条)
```

### 4.2 标每条约束时

```
1. 默念约束 name + source_text  → 这是要判什么?
2. 看 verifier 类型 → 用哪类标准?
3. 条件约束: 先判触发
4. 翻到对话原文找证据
5. 标 verdict + 写 evidence (要能直接证明 verdict!)
6. 不确定 → 标 review (不要硬猜!)
```

### 4.3 每标 5 通做的事

```
1. 休息 5 分钟
2. 起来走走、喝水、看远处
3. 不要"回头检查"刚标的(防自我催眠式调整)
```

### 4.4 标完整通后

```
1. 全约束 verdict 数大致分布:
   - pass 应占 60-70%
   - fail 应占 15-25%
   - na 应占 10-15%
2. 如果你这通对话标了 90% pass / 0% fail → 警报! 你疲劳了
```

### 4.5 标完 50 通后

```
1. 用 kappa_calc 自验 (跟 LLM 算)
2. 看是否有约束 kappa < 0.4 (这条约束规则你可能没弄懂)
3. 那些约束的 case 复核一遍
```

## 第 5 节: 7 个高频陷阱速查

### Q1: 约束没触发怎么标？

→ **na**，不是 pass！

例：V*_C11 "若骑手开车则挂断"，但用户全程没说开车 → **na**

**陷阱**：很多人误以为 "约束没被违反 = pass"。错！没触发不算"被遵守"，应 na。

### Q2: 约束部分满足？

→ 严格按约束的具体要求判：
- "必含 A 和 B" → 缺任一即 fail
- "做到 X 中至少 2 项" → 看具体数

### Q3: 对话被截断（断在第 3 轮）怎么标？

→ 后续 step 标 na (对话没走到), 已发生的 step 按实际判

### Q4: 模型说错了但用户原谅了？

→ 仍按约束本身判，**用户态度不影响 verdict**。
- 助手承诺补贴 → fail，不管用户是否说"那太好了"

### Q5: 用户态度让你心情受影响？

→ **忽略用户的语气**。你判的是**助手是否做到约束**，不是"用户是否满意"。

### Q6: 一个对话片段满足多条约束怎么办？

→ 每条约束**独立判定**。一个片段可以同时是多条约束的 evidence。

### Q7: 实在不确定？

→ **标 review**，绝对不要硬猜。review 的存在就是让你诚实。
